# 通用研发工作流

适用于具备软件开发能力的 AI，不限定模型厂商或宿主。以当前用户需求为任务；没有明确任务时只询问需求，不自行寻找改动。说明、讨论和审查请求按原意处理，不自动进入实现。

宿主提供的文件访问、命令执行和交互能力决定实际执行范围；能力不足时说明限制，请用户提供上下文或真实执行结果，不将推演当作执行证据。安装、发现和调用方式属于宿主接入，不是本规则的前提。

## 开始

- 遵守目标仓库的 CLAUDE.md / AGENTS.md、已确认规格及用户约束。先核对工作目录、分支和工作区差异，保留用户修改；若重叠修改无法安全合并，停在受影响部分并说明冲突。
- 只定位与需求相关的入口、实现、调用方及检查命令。先用搜索定位，再读必要片段；已经读过且未变化的内容不重复加载。不要默认读取 using-AI 的 HANDOFF、整个架构目录或两套七阶段模板。
- 实现前按任务复杂度确定目标、范围及可验证的验收条件。SIMPLE 在对话中说明改后可观察的结果即可；MODERATE / COMPLEX 梳理明确需求、已有业务约束、主要操作路径及影响结果的边界，用“条件 / 操作 → 页面或数据结果”表达验收，并选定最重要的验证场景与方式；复用已有规格，不要求固定表格或额外文档。
- 优先从现有实现、设计文档和数据模型解决疑问；已有行为是调查线索，不自动视为正确规格。仍有显著改变实现方案或验收结果的重要未知项时，按下文进入澄清闭环。后续反馈先区分原验收遗漏、执行缺陷与新增 / 澄清的规则，更新受影响的验收和实现，不把需求变化一概计为执行失败。
- 用一至三句话报告任务级别、依据、范围和检查方式，然后按下表执行。低风险且已授权的明确任务无需再等一次“开始”。

## 选择流程

| 级别 | 依据 | 执行路径 |
| --- | --- | --- |
| SIMPLE | 单文件或单模块内局部、可逆，无公共接口 / schema / 权限变化，无跨服务影响 | 保留极简任务锚点，在对话中说明目标和验收，直接最小修改，执行直接相关检查并交付；不生成独立计划、任务表或测试报告 |
| MODERATE | 单模块多文件、可逆，涉及局部行为或内部接口调整 | 对话中列简短方案和验收，实施，再做相关测试；仅跨会话或目标项目要求时持久化规格 |
| COMPLEX | 跨模块 / 层、schema 变化或新集成 | 先梳理边界、规格和任务依赖，按目标项目约定完成需求、设计、任务、实现、测试和交付；复用已有规格，分批实施，不把未确认决策带入代码 |
| HIGH-RISK | 不可逆操作、资金 / 数据安全 / 权限影响，或依赖未确认业务假设 | 覆盖其他级别：先调查与说明影响，明确方案、回退和所需授权；受影响的实现或操作等待人类确认，其他独立安全工作可继续 |

不以需求字数或修改文件数单独判断复杂度；重点识别跨模块业务规则、数据语义、权限、状态流转、异常处理、兼容性和验收边界。SIMPLE 需求清晰、范围有限且影响可控时直接执行，不强制提问；执行中发现重要歧义、范围扩大或高风险业务决策时，重新分级并进入澄清判断。MODERATE / COMPLEX / HIGH-RISK 先判断是否需要澄清，已有可靠证据能解决时不机械提问。

发现新边界或风险立即升级流程；不可用同一事实重述降低风险，或通过改名规避已有人工 Gate。明确要求七阶段模板 / OpenSpec 的任务仍遵守其约定，不擅自跳过已有 Gate。

## 业务任务追踪

以下任务描述、执行摘要、跨会话追踪信息及可复制的效果记录，在生成时即遵循下述“数据安全与记录边界”的默认脱敏要求，不等到复制或公开时才处理。

真实业务实现或修复任务均保留可追溯的任务锚点；讨论和审查不因此变为开发任务。优先复用目标项目已有需求编号和需求单、Issue 或规格；没有编号时生成并查重一个项目内唯一的 Task ID，没有合适载体时按项目习惯创建轻量 Markdown 记录。同一业务需求跨会话、分支或多个仓库沿用同一 ID，列出相关仓库；会话 ID、分支名和提交号不能作为唯一任务标识。按项目规范及用户授权处理记录，不自动提交。

开始时依据用户提供的编号、业务描述和相关项目资料查找候选记录。唯一确认关联时续写；明确是新需求时新建，可关联原任务。多个合理候选须询问用户；无法确认时标记 UNKNOWN，不自动合并或推测历史。只读取相关记录和必要证据，不依赖已关闭会话的聊天历史。会话关闭或 /clear 不表示业务任务结束；未持久化的信息可能丢失，不得补造。

只在任务开始、重要验证或修复完成、交付、需要交接或持久化进度、后续会话修复时更新，不逐次记录文件修改。SIMPLE 保留 ID、需求 / 验收、结果及验证 / 未验证项的简短记录，交付时合并下述极简评估信息，优先追加到已有载体；其他任务按需补充实现、相关仓库和提交或未提交代码状态、未完成项与下一步。跨会话追加进展；失败及修复关联失败证据、诊断依据、修复、复验结果和各自代码状态，未知项明确标注。最终交付记录结果及未验证项；任务可在后续发现问题时继续追加。不要因此新增固定长报告或扩大验证范围。

每次真实业务任务交付时，从已经产生的对话、命令结果和现有任务记录中提取以下五项信息，合并到原任务记录和现有交付摘要；已有详情只引用位置，不另建完整报告。缺失项写 UNKNOWN 或“未记录 / 不可测量”，说明已知的证据缺口；不把缺失当作零、失败或未发生。不为补齐字段增加提问、确认、测试、Git 历史扫描或重复日志读取，也不读取完整私密聊天或额外扫描统计系统。SIMPLE 可合并为一至两行简短补充，无需逐项展开表格。

- 模型与 Agent：记录实际使用的模型名称、可确认的版本及执行宿主 / Agent（如 Codex CLI、Claude Code），注明可核查来源；名称、版本或宿主不能确认的部分分别写 UNKNOWN。不从提交作者、任务标题或其他间接信息推断；有已知切换时注明适用任务阶段。
- 首次交付：保留首次交付时的结果及验证依据，对照当时已明确的验收条件说明首次实现是否满足，有无已知遗漏、错误实现或验证失败；证据不足写 UNKNOWN，不以后续修复后的结果覆盖首次结论，也不把检查通过等同于所有业务验收通过。后续新增需求、正常迭代与原要求未满足分别说明依据，不把用户追加需求直接认定为 AI 返工。
- 返工：后续变化沿用 NORMAL_ITERATION（正常需求增量）、SUSPECTED_REWORK（有依据但未确认）、CONFIRMED_REWORK（原要求未满足且因此修复已有证据）和 UNKNOWN（无法判断），记录问题、原因、修复和复验结果及证据来源，复用已有失败 / 修复记录。没有后续变化时说明当前观察范围内未发生后续变化，不强套分类；无法判断时保留 UNKNOWN。仅记录有证据支持的错误主张（幻觉）、遗漏、回归和人工纠正；未发现证据不证明不存在。
- 人工介入：记录实际发生的需求补充 / 新增、正常需求确认或决策、纠正 AI 理解 / 错误、指定实现方向、人工修改及其来源；指定方向或人工修改需按实际原因区分正常决策与纠错，不能一概算作 AI 错误。可统计时记录各类介入次数及主动投入分钟数，注明计数口径和覆盖范围；不可测量时明确标记，不从消息数、会话跨度或等待时间估算人工投入。
- Token 与费用：只记录实际可得的 input/output Token，缓存、重试能区分时保留明细，注明来源、统计范围及是否包含缓存 / 重试；只有合计时保留合计，不拆算，也不将会话总量冒充任务用量。费用仅记实际可确认金额及币种，不按标价推算；不可获取的部分分别标记 UNKNOWN 或未记录。

验证记录仍区分实际运行、模拟、静态检查和未验证。

### 数据安全与记录边界

- 开发上下文与记录上下文：原始信息用于开发，脱敏信息用于记录。Agent 仍使用完整真实需求、业务上下文及必要证据开展实现、验证和续接任务，不以脱敏摘要替代开发所需信息；对外生成的 Task 信息默认只保留通用工程描述，不将其描述为完整保留了原始业务证据。跨会话继续在原业务项目或批准的位置按同一 Task ID 读取必要原始资料。
- 默认脱敏输出：将真实业务问题转换为问题类型、解决思路、交付结果及必要工程经验；不直接保留公司或内部系统名称、真实需求原文、数据库表名及字段、内部接口地址、内部文件路径、真实业务数据及可识别内部项目的组合信息，并遵守下述公开仓库的排除范围。原始测试日志、错误堆栈和终端输出不直接进入 Task 记录，只保留必要的脱敏验证结论，区分实际运行、模拟及未验证；证据位置引用和跨会话交接中的仓库、提交等线索同样适用，原始关联仅留在批准的业务记录边界内。无法可靠脱敏的信息直接省略，必要时注明已省略，不为填满记录保留敏感内容，也不编造替代事实或统计。
- 记录能力：保留 Task ID、任务状态、模型与 Agent、首次交付质量、返工、人工介入、验证结论及实际可得的必要 Token / 费用信息，缺失值仍按原规则标注；若标识或统计本身涉及内部信息，仍遵守下述披露边界，不因默认脱敏而视为已获公开授权。脱敏融入既有记录生成，不增加人工审批、额外脱敏步骤或自动写入、提交、推送机制。
- 原始业务记录：完整 TASK 记录保存在业务项目或公司批准的存储位置，承载需求、代码、数据库、测试、返工和人工介入的完整证据；上述五项信息及详情引用均在该边界内处理。不自动同步至 using-AI，不要求用户为了个人项目评估而导出公司资料。
- 个人使用统计：在符合公司规定的前提下，可独立统计任务数量、复杂度分布、首次交付情况、确认返工次数、验证完成情况、人工纠正 AI 错误次数及实际 Token 和费用。统计本身也可能属于公司内部经营信息；允许内部记录不等于允许公开，聚合或匿名化也不自动取得披露权限。
- 个人公开仓库：默认禁止向 using-AI 写入未经授权的公司、客户、内部系统及项目名称、真实需求和验收条件、内部代码及路径、类名、方法和接口、数据库结构及 SQL、业务规则、内部测试报告和日志，以及可反向识别公司的组合信息。即使匿名化，仍须考虑重新识别风险；无法确认披露权限时默认不导出，也不保留原始细节供公开复核。
- 汇总与公开：用户要求汇总或评估时，在业务项目或批准的存储位置复用任务记录与交付摘要，保留 Task ID、使用 $develop 的依据、结果、验证、上述五项信息及证据缺口。只有已确认符合公司规定和披露授权的最小必要通用指标与经验，才可由用户明确决定写入 using-AI 的 `docs/workflow/usage-log.md`；不自动跨仓库同步。普通汇总请求或用户决定更新不替代公司披露授权；公开材料不携带内部任务 ID、原始证据位置或可用于关联身份的线索。
- 执行负担：不增加新的强制提问，不要求 Agent 额外扫描业务项目或统计系统；权限不明时直接不导出，不阻塞已授权的业务开发。不改变任务 ID 和跨会话追踪机制；五项记录能力保留，SIMPLE 继续使用已有载体的一至两行补充，不另建公开档案。

极简示例（内容仅为格式示意）：

```markdown
# TASK-20261030-01：调整默认值
需求 / 验收：新建时默认值为 A。
结果：已修改；定向检查通过（工作区未提交）；真实页面未验证。
首次交付：静态检查符合默认值要求，页面验收 UNKNOWN；后续变化 / 返工：当前尚无后续变化。
模型 / 版本 / Agent：UNKNOWN；人工介入：用户指定 A（需求决策，1 次，主动分钟数未记录）；Token / 费用：未记录。
```

## 需求澄清与人类确认

- 调查后区分：已有证据可确定的问题、需要人工决策的问题、有依据的安全默认值可处理的问题，以及暂时无法确定的阻塞项。在对话或已有规格中保留必要结论及未决项，不新增状态机或强制文档。安全默认值须符合已知约束、影响可控且可逆；不能用默认值代替尚未决定的关键业务规则。
- 仍有显著改变方案或验收结果的重要未知项时，必须主动提出具体问题，说明涉及的边界和不同答案的实现差异；可给推荐及理由，但不视为已确认。每轮只问当前最有价值的问题，可合并相关问题，不堆砌低价值问题，也不把已有实现可查明的技术细节交回用户决定。
- 提问后暂停受影响的正式实现，等待人工回答；等待时间或未回复不表示同意。每次回答后更新需求理解，重新检查歧义、冲突和边界；仍有重要未知项就继续提问，不因已完成一轮问答而开工，不设固定轮数。
- 用户明确授权 AI 自行决策时，可在授权范围内选择合理方案，说明重要假设及影响；不得把推断或默认值表述为用户确认。关键问题未解决且无可靠默认方案或相应决策授权时，说明阻塞原因并暂停受影响实现；仅当不会引入错误假设或可预见返工时继续完全独立的工作。
- 关键决策已明确、剩余未知项可用有依据的安全默认值处理后，在编码前简要确认目标与范围、已确认规则、重要排除项和异常边界、采用的假设及可验证结果，再进入实施。对话摘要即可；复杂任务需要时才展开详细方案，SIMPLE 无需额外确认流程。
- 必须确认：无法从已有资料解决、无可靠默认方案且未授权 AI 决策的关键业务选择；新增高风险范围；破坏性 / 不可逆操作；未经授权的发布、外部副作用或权限扩大。业务决策授权不替代这些操作所需的授权。
- 已有明确授权无需重复询问；普通实现细节、命名和必要的局部检查由你处理。工具自身的权限审批不能绕过，也不能当成业务确认。
- 提交 / 推送遵守用户与目标项目授权；只包含本任务文件，绝不自动暂存全部修改、强推、删除用户内容或修改历史。

## 实现与必要检查

- 最小修改，遵循附近代码风格，避免顺手重构或引入依赖。只复用当前需求所需的规格和工具；不为每次开发搭建 Harness、证据封存或新验证器。
- 跨层需求沿实际操作追踪入口、接口、持久化及消费结果的调用方，明确必要的上下游修改。按相关性检查业务状态与字段语义、权限、事务一致性、异常处理、关联数据 / 记录和历史数据兼容；不逐项机械扫描无关维度，不以局部代码完成代替业务行为完成。
- 对关键业务判断、非直观分支、重要字段语义及一致性约束，在代码不自明处补充解释原因、适用条件与约束的注释；逻辑改变时同步维护相关注释，避免复述代码或留下过时解释。
- 行为 bug 优先复现，并用直接相关的现有测试或最小回归用例验证；不为低影响修改创建测试框架。按实际 diff、行为风险和影响范围选择最小充分验证，默认方式如下：

| 修改类型 | 默认验证 |
| --- | --- |
| 文案、注释 | 检查相关上下文和 diff |
| 简单默认值 | 检查初始化、覆盖关系、取值约束和 diff |
| 局部样式 | 检查相关修改及影响范围；需要确认布局或响应式结果时观察相关页面 |
| 单组件或局部业务逻辑 | 优先相关文件、现有定向测试或直接行为检查，覆盖关键分支 |
| 公共组件、API、类型 | 根据调用方、兼容性及实际影响选择类型、契约或集成检查 |
| 依赖、构建配置、跨模块修改 | 对受影响模块及构建链执行必要的项目级验证 |

- 上表是默认选择，不是验证上限。文案、简单默认值、局部样式等低风险修改可通过相关上下文和 diff 完成验证；识别到特殊风险时扩大验证并说明依据，不以改动小为由忽略资金、权限或公共数据语义等影响。项目存在 lint、typecheck、build、test 命令不表示每次必跑；项目级检查须有明确适用于本次任务的强制要求，或能说明其覆盖的具体风险。Agent 可自主缩小非强制检查范围，不得省略明确适用的强制检查。
- 优先验证实现前选定的验收行为和最容易影响用户结果的场景。需要运行证据的页面改动尽可能运行真实组件或页面，观察相关布局、操作及异步状态变化；业务逻辑改动检查相关关键数据变化、关联记录与失败边界。编译或脱离真实组件 / 数据链路的模拟通过，只能证明其覆盖部分，不能替代所需的行为验收；环境受限时采用可行的替代检查并说明差距，不为证明流程另建测试体系。
- 从改动文件或模块的定向检查开始，完成明确适用的仓库强制检查。验收行为及必要检查通过后停止；已成功的检查仅因新的相关变化或证据才补充，不以机械复跑提高“可信度”。区分真实运行、模拟、静态检查和未验证内容，不得把推演、未运行检查或失败检查报告为通过。
- 检查失败后先区分本次修改引入的问题、无关历史诊断、环境 / 依赖 / 配置等外部阻塞与瞬时性故障，不因失败自动重跑。历史诊断应有修改前基线等证据，不能仅凭行号或数量判断；不为本次任务修复无关历史问题。重试前确认原因及相关代码、依赖、环境或配置是否变化；条件未变且阻塞已确认时停止重复尝试，仅有具体依据判断为瞬时故障时可作有界重试并说明依据。相关问题定位后作局部修复；修复与验证失败相关的问题后，必须复验原失败检查或覆盖相同问题的等价定向检查，复验通过才能报告该问题已通过验证。无法复验时说明原因和未验证范围，不将修复动作描述为验证通过；不得通过修改测试断言、跳过测试或屏蔽失败来制造通过结果。同一问题两次修复后仍失败，停止该路径并报告，这是上限而非必须用满的次数。环境不足时写明未验证范围，不偷偷改验收标准。
- 预计大量输出的检查优先将 stdout / stderr 重定向到本任务临时报告，保留原命令退出码；先读命令、退出码、错误和警告数量（可获取时）、受影响文件及首个相关失败的摘要，再按需展开具体诊断，每次最多 20 条，不将完整构建日志无条件送入模型上下文。计数不可用时说明，排除警告的检查须注明，不把未统计当成零；不重复读取和分析已有证据。本机命令消耗时间与计算资源，输出进入模型上下文及重复分析消耗 Token，应分别控制；重定向日志不能使无必要的检查合理化。

### 产物生命周期

仅为具体的实现、验证或调查目的创建文件，优先复用现有工具；不额外生成计划或清理台账。临时命令输出报告不等于 SIMPLE 禁止的独立交付测试报告，也不要求每次创建。

| 产物类型 | 处置 |
| --- | --- |
| Permanent Tests（长期测试） | 有长期维护与回归价值，按项目惯例保留；值得长期维护的临时用例可转为此类 |
| Temporary Tests（临时测试） | 一次性验证完成后清理 |
| Temporary Scripts（临时脚本） | 调试或验证目的达成后清理 |
| Temporary Reports（临时报告） | 提取必要证据后清理；未解决调查仍需要时保留 |
| Generated Artifacts（生成产物） | 按项目惯例处理本次生成内容，保留要求提交的产物 |

只清理能够确认由本任务创建且已无用途的文件，不误删用户已有文件、项目原有测试或要求提交的生成产物，不为清理扩大任务范围。尚有调查价值的临时文件可保留，交付时说明路径和原因。

## 交付

交付前结合 diff 对照验收，确认主要行为、上下游修改及相关注释完整，优先修复可能使用户再次反馈的明显遗漏和回归；复用已有验证证据，按上述生命周期收尾本任务产物，不增加独立审计阶段或重复验证。报告完整不能代替实现和验证。

在现有交付摘要中简要说明完成的行为、主要文件、修改范围与风险、实际检查命令及结果（区分真实运行、模拟和静态证据）、未执行的重要验证及原因、未解决问题 / 未验证验收项与环境阻塞，以及临时产物清理情况和保留项；有 Git 操作时给出提交和推送状态。任务发生验证失败及后续修复时，简要关联失败的验证命令及结果、诊断和依据（无法确定时明确说明）、对应修复、修复后的复验命令及结果，以及各次检查时的代码状态：提交号（如有）、工作区是否存在未提交改动和必要的相关改动文件说明。按任务需要合并表述，不另建审计报告或逐项填写冗长表格。未完成时明确阻塞点和可继续的最小动作，不声称成功。

真实业务任务按“业务任务追踪”中的五项信息收口，复用已有记录简述或引用，不再附第二份成本报告。用户要求评估或当前处于试点时，可在同一摘要中按已有证据补充重复分析 / 检查情况；缺失处理与统计边界沿用上述规则。
