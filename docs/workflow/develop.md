# 通用研发工作流

适用于 Codex CLI 与 Claude Code 的开发请求。以当前用户需求为任务；没有明确任务时只询问需求，不自行寻找改动。说明、讨论和审查请求按原意处理，不自动进入实现。

## 开始

- 遵守目标仓库的 CLAUDE.md / AGENTS.md、已确认规格及用户约束。先核对工作目录、分支和工作区差异，保留用户修改；若重叠修改无法安全合并，停在受影响部分并说明冲突。
- 只定位与需求相关的入口、实现、调用方及检查命令。先用搜索定位，再读必要片段；已经读过且未变化的内容不重复加载。不要默认读取 using-AI 的 HANDOFF、整个架构目录或两套七阶段模板。
- 实现前按任务复杂度确定目标、范围及可验证的验收条件。SIMPLE 在对话中说明改后可观察的结果即可；MODERATE / COMPLEX 梳理明确需求、已有业务约束、主要操作路径及影响结果的边界，用“条件 / 操作 → 页面或数据结果”表达验收，并选定最重要的验证场景与方式；复用已有规格，不要求固定表格或额外文档。
- 优先从现有实现、设计文档和数据模型解决疑问；已有行为是调查线索，不自动视为正确规格。仍有显著改变实现方案或验收结果的重要未知项时，按下文进入澄清闭环。后续反馈先区分原验收遗漏、执行缺陷与新增 / 澄清的规则，更新受影响的验收和实现，不把需求变化一概计为执行失败。
- 用一至三句话报告任务级别、依据、范围和检查方式，然后按下表执行。低风险且已授权的明确任务无需再等一次“开始”。

## 选择流程

| 级别 | 依据 | 执行路径 |
| --- | --- | --- |
| SIMPLE | 单文件或单模块内局部、可逆，无公共接口 / schema / 权限变化，无跨服务影响 | 在对话中保留目标和验收，直接最小修改，执行直接相关检查，交付；不生成独立计划、Spec、任务表或测试报告文件 |
| MODERATE | 单模块多文件、可逆，涉及局部行为或内部接口调整 | 对话中列简短方案和验收，实施，再做相关测试；仅跨会话或目标项目要求时持久化规格 |
| COMPLEX | 跨模块 / 层、schema 变化或新集成 | 先梳理边界、规格和任务依赖，按目标项目约定完成需求、设计、任务、实现、测试和交付；复用已有规格，分批实施，不把未确认决策带入代码 |
| HIGH-RISK | 不可逆操作、资金 / 数据安全 / 权限影响，或依赖未确认业务假设 | 覆盖其他级别：先调查与说明影响，明确方案、回退和所需授权；受影响的实现或操作等待人类确认，其他独立安全工作可继续 |

不以需求字数或修改文件数单独判断复杂度；重点识别跨模块业务规则、数据语义、权限、状态流转、异常处理、兼容性和验收边界。SIMPLE 需求清晰、范围有限且影响可控时直接执行，不强制提问；执行中发现重要歧义、范围扩大或高风险业务决策时，重新分级并进入澄清判断。MODERATE / COMPLEX / HIGH-RISK 先判断是否需要澄清，已有可靠证据能解决时不机械提问。

发现新边界或风险立即升级流程；不可用同一事实重述降低风险，或通过改名规避已有人工 Gate。明确要求七阶段模板 / OpenSpec 的任务仍遵守其约定，不擅自跳过已有 Gate。

## 需求澄清与人类确认

- 调查后区分：已有证据可确定的问题、需要人工决策的问题、有依据的安全默认值可处理的问题，以及暂时无法确定的阻塞项。在对话或已有规格中保留必要结论及未决项，不新增状态机或强制文档。安全默认值须符合已知约束、影响可控且可逆；不能用默认值代替尚未决定的关键业务规则。
- 仍有显著改变方案或验收结果的重要未知项时，必须主动提出具体问题，说明涉及的边界和不同答案的实现差异；可给推荐及理由，但不视为已确认。每轮只问当前最有价值的问题，可合并相关问题，不堆砌低价值问题，也不把已有实现可查明的技术细节交回用户决定。
- 提问后暂停受影响的正式实现，等待人工回答；等待时间或未回复不表示同意。每次回答后更新需求理解，重新检查歧义、冲突和边界；仍有重要未知项就继续提问，不因已完成一轮问答而开工，不设固定轮数。
- 用户明确授权 AI 自行决策时，可在授权范围内选择合理方案，说明重要假设及影响；不得把推断或默认值表述为用户确认。关键问题未解决且无可靠默认方案或相应决策授权时，说明阻塞原因并暂停受影响实现；仅当不会引入错误假设或可预见返工时继续完全独立的工作。
- 关键决策已明确、剩余未知项可用有依据的安全默认值处理后，在编码前简要确认目标与范围、已确认规则、重要排除项和异常边界、采用的假设及可验证结果，再进入实施。对话摘要即可；复杂任务需要时才展开详细方案，SIMPLE 无需额外确认流程。
- 必须确认：无法从已有资料解决、无可靠默认方案且未授权 AI 决策的关键业务选择；新增高风险范围；破坏性 / 不可逆操作；未经授权的发布、外部副作用或权限扩大。业务决策授权不替代这些操作所需的授权。
- 已有明确授权无需重复询问；普通实现细节、命名和必要的局部检查由你处理。工具自身的权限审批不能绕过，也不能当成业务确认。
- 提交 / 推送遵守用户与目标项目授权；只包含本任务文件，绝不自动暂存全部修改、强推、删除用户内容或修改历史。

## 实现与必要检查

- 最小修改，遵循附近代码风格，避免顺手重构或引入依赖。只复用当前需求所需的规格和工具；不为每次开发搭建 Harness、证据封存或新验证器。
- 跨层需求沿实际操作追踪入口、接口、持久化及消费结果的调用方，明确必要的上下游修改。按相关性检查业务状态与字段语义、权限、事务一致性、异常处理、关联数据 / 记录和历史数据兼容；不逐项机械扫描无关维度，不以局部代码完成代替业务行为完成。
- 对关键业务判断、非直观分支、重要字段语义及一致性约束，在代码不自明处补充解释原因、适用条件与约束的注释；逻辑改变时同步维护相关注释，避免复述代码或留下过时解释。
- 行为 bug 优先复现，并用直接相关的现有测试或最小回归用例验证；文字或静态配置修改使用相称检查，不为低影响修改创建测试框架。
- 优先验证实现前选定的验收行为和最容易影响用户结果的场景。页面改动尽可能运行真实组件或页面，观察相关布局、操作及异步状态变化；业务逻辑改动检查关键数据变化、关联记录与相关失败边界。编译或脱离真实组件 / 数据链路的模拟通过，只能证明其覆盖部分，不能替代行为验收；环境受限时采用可行的替代检查并说明差距，不为证明流程另建测试体系。
- 从改动文件或模块的定向检查开始，再完成目标仓库要求的检查。验收行为及必要检查通过后停止；仅对后续修改影响的检查、新失败或明确未解决风险补充验证，不以机械复跑提高“可信度”。区分真实运行、模拟、静态检查和未验证内容，不得把推演、未运行检查或失败检查报告为通过。
- 若检查失败，先定位原因后作局部修复；同一问题两次修复后仍失败，停止该路径并报告，不循环消耗。环境不足时写明未验证范围，不偷偷改验收标准。

## 交付

交付前结合 diff 对照验收，确认主要行为、上下游修改及相关注释完整，优先修复可能使用户再次反馈的明显遗漏和回归；复用已有验证证据，不增加独立审计阶段或重复验证。报告完整不能代替实现和验证。

简洁报告：完成的行为、主要文件、实际检查命令及结果（区分真实运行、模拟和静态证据）、未解决问题 / 未验证验收项及环境阻塞；有 Git 操作时给出提交和推送状态。未完成时明确阻塞点和可继续的最小动作，不声称成功。

只有用户要求评估或当前处于试点时，附一行成本记录：实际可获取的 input/output Token（含缓存与重试，注明来源和边界）、人工介入次数 / 主动分钟数、重复分析 / 检查、返工。不可测项写“不可测量 / 未记录”，不得用估计值代替实测，不因收集用量读取原始私密会话或开发统计系统。
